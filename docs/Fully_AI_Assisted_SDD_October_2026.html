2. Introduction

2.1 Subject and scope

Spec-driven development (SDD) uses explicit specifications to direct design, implementation, tests, and later changes. Specifications remain active references throughout the software life cycle.

In this report, AI writes every new or changed line of project code. This includes application code, tests, database queries, migration scripts, build scripts, and executable configuration. AI also drafts specifications, design records, plans, and operating instructions. Humans supply facts, make decisions, request changes in plain language, and approve results.

The scope includes production applications, microservices, scripts, engineering workflows, data workflows, and long-lived enterprise systems. The workflow applies to new projects and changes to existing systems. It does not require a particular language, editor, model, or SDD toolkit.

The report excludes vibe coding, alternative meta-level development frameworks, forecasts, employment effects, and prototype development. Security and compliance are outside its assessment. The production criteria below address the engineering areas within this scope.

Zero manual coding is an authorship constraint. It does not make a release correct, remove technical judgment, or require an unattended process.

2.2 The state of the practice in October 2026

Current tools support the mechanics needed for this workflow. Tool documentation establishes capabilities. It does not establish that every generated system meets production requirements.

Observed capability Primary-source evidence What the evidence does not establish
Specifications can drive plans, tasks, implementation, and checks. GitHub introduced Spec Kit in September 2025. Its current SDD guide includes clarification, analysis, implementation, and convergence checks. [1] [2] A convergence label does not prove the specification is complete or the product fits its purpose.
Requirements, design, and tasks can persist as separate project files. Kiro documents these artifacts. Its Feature Specs support requirements-first and design-first paths. [3] [24] A generated document does not become an approved requirement merely because the tool created it.
Coding tools can make coordinated changes across files and run checks. Claude Code documents repository search, file editing, command execution, and feedback from tool results. [4] Access to the whole repository does not mean the model reads or understands every file.
Tools can help derive tests from requirements. Kiro documents property-based tests. Its capability table limits this feature to its IDE. [22] Sampled tests do not prove correctness for every possible input.

Engineering judgment: A zero-manual-code workflow is feasible where the available AI tools can implement the work and the team can establish adequate evidence. It is not a universal delivery guarantee.

The sources reviewed here do not establish a general success rate for fully AI-written, production SDD across these system types. This report makes no numerical claim about quality gains, delivery speed, or the probability of success. A blocked implementation remains blocked until AI produces an acceptable result or the team approves a different design or scope.

2.3 How to read this report

Section 4 gives the whole process. Section 5 explains thirteen stages with the same decision and evidence structure. Section 6 defines terms. The appendices give concise review aids.

Evidence labels: Statements about tools cite their documentation. The recommended workflow is an engineering synthesis of those capabilities and established software engineering methods. All example requirements, identifiers, thresholds, and outcomes are illustrative. No example reports an executed software project.

References include publication or update dates where the source gives them. “Undated” means that the cited page gives no publication date. All sources were checked on October 16, 2026. Living documentation can change after that date.

3. Assumptions

Assumption Practical consequence
Humans know the intended work and can reach its subject experts. AI can organize requirements, but cannot invent authoritative business rules.
The team has access to architecture, testing, and code-review competence. A product manager can direct the process. A qualified technical reviewer assesses decisions beyond that manager’s expertise.
The AI tool can inspect files, edit multiple files, run commands, and read results. A text-only chat cannot complete the whole local workflow without another execution mechanism.
A suitable runtime and representative test environment are available. AI can generate setup files and run installation or build steps. An unavailable dependency remains an explicit blocker.
Humans can inspect outputs and, when needed, read code. Reading, questioning, and rejecting code do not require writing code. AI performs all requested edits.
The team can define expected results independently of the generated implementation. Business examples, reference calculations, interface contracts, and operating limits can serve as test oracles.
The repository retains versions of the specification, implementation, and evidence. A decision or result remains available after a conversation ends.
Production targets are specific to the intended use. A weekly script needs different operating evidence from a continuously available service.

Authorship boundary: “100%” applies to the project code produced or changed through this workflow. Existing code and third-party libraries retain their original authorship. A team must not describe an inherited repository as entirely AI-authored because AI changed part of it.

No manual coding fallback: Humans can approve installation, run an AI-supplied command, or supply data through an interface. They do not write code, tests, SQL, shell scripts, configuration syntax, or patches. If a tool asks for such an edit, ask AI to perform it or create the complete artifact.

4. SDD at a high level

4.1 The operating model

The specification states required behavior and measurable constraints. The design explains how the system will meet them. The plan divides the design into reviewable work. AI implements each increment and supplies evidence. Humans assess the evidence against the approved intent.

SDD does not require one large specification before all development starts. Establish the system boundaries first. Then specify, design, implement, and accept a bounded change. New evidence can require a specification or design change before implementation continues.

A failed check returns work to the artifact that contains the error. A code defect needs a code change. A missing business rule needs a requirement decision. Repeated code generation cannot resolve an undecided business rule.

4.2 The minimum set of durable artifacts

File names below are examples. A small script can combine documents. A large system can divide them by component or feature.

Artifact Required content Authority
spec.md Goals, scope, behavior, exclusions, requirement IDs, acceptance examples, and measurable quality targets Approved intended behavior
design.md and decision records Components, interfaces, data, dependencies, failure handling, and decision reasons Approved implementation constraints
plan.md Ordered tasks, dependencies, requirement links, checks, and stop conditions Authorized work for the increment
acceptance.md and test assets Expected results, fixtures, test levels, and test-to-requirement links Approved basis for assessment
Source, build, and dependency files Implementation, tests, version constraints, and reproducible setup The actual software under assessment
evidence.md Commit, environment, commands, results, defects, and untested areas What the team actually observed
handover.md Setup, operation, recovery, interfaces, known limits, and ownership Instructions checked against the release

A chat message does not silently replace an approved artifact. Ask AI to record a proposed change, show its effects, and wait for the required decision. Version the accepted specification with the corresponding code. Spec Kit documents a living-spec approach with downstream updates after specification changes. [20]

4.3 A coding agent, precisely defined

A coding agent is a software system that observes a development environment, selects actions toward a task, uses tools, and responds to their results. Its autonomy is bounded by the task, available tools, and stop conditions. This definition draws on established agent concepts and current tool behavior. [4] [21]

A language model that only returns a code block is not, by that fact alone, a coding agent. “Agentic” describes the action-and-feedback behavior. It does not establish intelligence, correctness, or independence from human decisions.

One coding agent can work across many files. Several prompts with different role labels do not necessarily create a multi-agent system. Multiple independently controlled agents can divide work, but shared interfaces and integration still need explicit ownership. More agents are not a requirement of SDD.

4.4 Two distinct questions about correctness

Question Activity Typical evidence
Does the software meet the approved specification? Verification Tests, analysis, code inspection, and measured constraints
Does the specified software serve the intended use? Validation Representative user tasks, domain review, and accepted outcomes

A system can pass its tests and still solve the wrong problem. NASA’s systems engineering guidance distinguishes these two activities. Both belong in this workflow. [8]

The test oracle problem: A test needs a basis for deciding what is correct. Generating both code and expected results from one mistaken assumption can produce a false pass. Domain examples and independently checked expected results reduce that circularity. A second AI review can find defects, but does not guarantee independent judgment. [9]

4.5 Traceability through one production change

Consider an existing data-import service that must handle repeated requests without duplicate writes. The following is a requirements example, not a prototype build.

Record Illustrative content
REQ-017 When the service receives the same import ID and payload within 24 hours, it must return the original result without another write.
REQ-018 If an import ID repeats with a different payload within 24 hours, the service must reject the request without a write.
DEC-006 Store the request identifier, payload identity, and result with the write in one transactional design. Review crash and concurrency behavior.
TASK-012 Implement duplicate detection, result retrieval, and conflict handling across storage, service, and interface files.
TEST-031–035 Check sequential repeats, simultaneous repeats, changed payloads, restart recovery, and expiration of the 24-hour window.
EVID-009 Record the tested commit, database version, input fixtures, commands, and results. Mark tests that did not run.

These requirements still need decisions about payload equivalence, the time reference, expiration behavior, and concurrent requests. AI must expose these questions before the team approves the design. Every production change needs its own complete definition.

5. SDD in detail

How the stages fit together

The stages describe responsibilities, not a one-way sequence. Review each increment. Prepare tests before implementation where practical. Maintain documents as work changes. Repeat the relevant stages for defects and later requirements.

Common prompt contract: Identify the authoritative artifacts and versions. State the allowed change and required output. State what must remain unchanged. Define checks, evidence, and stop conditions. Treat any unapproved assumption that changes behavior as a question.

Prompts below use plain language. Humans can supply the values in brackets through conversation. AI writes all files and executable syntax.

015.1 Define the outcome and boundaries

Purpose Establish the problem, intended users, accepted scope, and decision owners before AI proposes software.

Recommended practices Describe real tasks and their outcomes. Record the current problem, operating environment, exclusions, and delivery constraints. Assign product, technical, and release decisions to named people or roles. One person can hold several roles.

Give or ask the AI Supply process descriptions, examples of inputs and outputs, existing obligations, and the reason for the change. Ask for a concise scope statement, a terms list, and questions ranked by their effect on the design. AI must distinguish supplied facts from proposed assumptions.

Human decision and check Approve the outcome and boundaries. Decide what a failed delivery would look like. Reject features that AI adds without a requirement.

Common mistake → recovery “Build an enterprise-ready application” has no measurable meaning. Replace it with observable tasks, operating limits, and acceptance conditions. If the scope expands, revise the approved boundary before planning more work.

Exit evidence An approved scope statement, decision owners, and an open-question list with owners.

Reusable prompt: Draft the scope from these facts: [facts]. Separate requirements, assumptions, and questions. Include intended users, outcomes, constraints, and exclusions. Ask the highest-impact unresolved question first. Do not design or implement the system yet.

025.2 Inspect the system and establish a baseline

Purpose Give AI a factual starting point and make existing behavior reproducible.

Recommended practices Ask AI to inspect the repository, interfaces, build files, dependencies, tests, and relevant documents. Require file references for findings. Record runtime versions and current test results. For an existing system, identify callers, stored data, compatibility obligations, and known defects. For a new system, establish the approved build and test environment.

Give or ask the AI Supply repository access, current specifications, sample data, interface documents, and environment constraints. Ask AI to create setup files and run the baseline checks. Keep persistent instructions short. Store detailed behavior in the specification, then reference the relevant sections for each task.

Human decision and check Confirm that the inspected system and environment are the right ones. Decide which observed behaviors must remain. A characterization test records existing behavior. It does not prove that behavior is desirable.

Common mistake → recovery AI guesses a library interface or treats old comments as current truth. Require the installed version, source location, or official documentation. If existing tests fail, record the failure before a new change so that it cannot hide a new regression.

Exit evidence A system map, version record, baseline results, and explicit unknowns. Claude Code documents repository exploration and planning before edits. [23]

Reusable prompt: Inspect [repository and documents] without changing application behavior. Map the relevant files, interfaces, dependencies, and tests. Run the existing checks. Cite evidence for each finding. Record baseline failures and missing access. Generate any required setup artifacts for review.

035.3 Specify behavior and acceptance criteria

Purpose Turn intent into requirements that the team can assess without guessing.

Recommended practices Give each requirement a stable ID. Describe one behavior with its conditions and observable result. Include normal, boundary, invalid-input, and failure cases. State priority and exclusions. Specify measurable quality attributes, such as completion time, data precision, capacity, and recovery behavior.

Give or ask the AI Supply business rules, units, calendars, representative data, and independently checked examples. Ask AI to find contradictions, missing states, vague terms, and assumptions. Use decision tables or state diagrams when prose becomes ambiguous. EARS supplies patterns for structured natural-language requirements. Its syntax helps clarity but does not establish completeness. [6]

Human decision and check Approve behavior and expected results. Resolve terms such as “duplicate,” “latest,” “success,” and “business day.” Decide numerical thresholds. AI can propose them, but must label them as proposals.

Weak statement Testable replacement, using illustrative values
The import must be fast. For the approved 100,000-row fixture, the import must finish within 60 seconds on environment E-01.
Handle errors gracefully. If any row has an invalid date, reject the file, identify the row, and leave stored data unchanged.
Preserve precision. Convert inputs to the approved unit, then round the result to two decimals using the stated rounding rule.

Common mistake → recovery A polished document hides unanswered questions. Review examples and contradictions before wording. Block only the affected work when a requirement lacks a decision.

Exit evidence Approved requirements, examples, measurable constraints, and a list of unresolved items outside the authorized increment.

Reusable prompt: Draft requirements from [approved scope and facts]. Assign stable IDs. Include conditions, results, boundary cases, and acceptance examples. Flag contradictions and missing decisions. Propose measurable quality targets separately. Do not invent business rules or implement code.

045.4 Design the system and its contracts

Purpose Choose a technical structure that meets the requirements and supports later changes.

Recommended practices Compare a small number of viable designs against the most important constraints. Describe component responsibilities, dependencies, data ownership, state transitions, and failure handling. Choose the language, framework, major libraries, and supported versions. Record decision reasons and rejected alternatives. Attribute-Driven Design offers a foundation for decisions driven by significant requirements. [7]

Give or ask the AI Supply the specification, existing architecture, platform restrictions, expected workloads, and team operating limits. Ask for component and sequence diagrams, interface contracts, a data model, and a requirement-to-design map. For an HTTP interface, AI can generate an OpenAPI description from the approved contract. [10]

Human decision and check Approve trade-offs about consistency, latency, complexity, compatibility, and operating cost. Check whether the design explains failures between steps. Ask who owns each piece of state and how incomplete work recovers.

Common mistake → recovery AI adds services, queues, or abstraction layers because they appear in familiar patterns. Require a requirement that justifies each major component. If uncertainty blocks a decision, use source inspection, calculation, or tests against the real dependency. Record the limit until evidence resolves it.

Exit evidence Approved design records, contracts, dependency choices, and an explicit treatment of the important failure paths.

Reusable prompt: Propose the simplest design that meets [requirement IDs] within [constraints]. Compare the viable alternatives. Include component responsibilities, contracts, data rules, failure behavior, and dependency versions. Link decisions to requirements. Identify unresolved trade-offs for human approval before implementation.

055.5 Plan small, verifiable increments

Purpose Convert the approved design into work that AI can finish and humans can assess.

Recommended practices Plan vertical slices that deliver observable behavior across the needed layers. State dependencies and order. Include test work, data changes, documentation, and release implications. Separate behavior changes from unrelated refactoring. Keep each increment small enough for a meaningful review, without imposing an arbitrary line limit.

Give or ask the AI Request a task table with requirement IDs, affected components, likely files, dependencies, tests, and completion evidence. Ask for gaps between the specification, design, and plan. A file list is a starting assumption, not permission to ignore a necessary related change.

Human decision and check Approve the sequence, scope, and evidence for each task. Confirm that early increments use the intended architecture and meet the quality criteria applicable to their behavior. An incomplete product can contain production-quality increments.

Common mistake → recovery A single task says “implement the backend.” Divide it by externally observable behavior. If tasks are too interdependent for separate review, revise the interface boundaries or combine the tightly coupled work.

Exit evidence An approved plan with no unexplained requirement gaps and no hidden implementation decisions. Spec Kit’s current process includes artifact analysis before implementation and a later convergence check. [2]

Reusable prompt: Derive an incremental plan from [approved specification and design]. For each task, list requirement IDs, dependencies, affected components, tests, and completion evidence. Include integration and documentation work. Identify inconsistencies. Stop before implementation until I approve the plan.

065.6 Establish tests and expected results

Purpose Define how the team will detect incorrect behavior before it accepts the implementation.

Recommended practices Derive acceptance tests from approved examples. Ask AI to create unit, integration, and contract tests where each adds useful evidence. Include rejected inputs, boundaries, interrupted work, repeated operations, and concurrency when relevant. Use property-based tests for rules that hold across a range of inputs. Hypothesis is one implementation for Python. [12]

Give or ask the AI Supply expected outputs, reference calculations, invariants, and representative fixtures. Ask which requirements each test checks and which remain uncovered. Require assertions about observable results. For defect repairs, show the regression test failing for the intended reason before the repair and passing after it.

Human decision and check Approve expected results and tolerances. Check that mocks do not replace the behavior under assessment. Ask whether a deliberately wrong result would fail the test. AI can create a controlled mutation or a known-bad input to check that property.

Common mistake → recovery AI copies its implementation logic into the expected-result calculation. Replace that calculation with independently checked examples or a distinct reference method. A compile error is not evidence that a behavioral test detects the intended defect.

Exit evidence A reviewed test design, AI-written test assets, credible expected results, and a clear coverage map. The oracle problem remains even when test generation is automated. [9]

Reusable prompt: Create tests for [requirement IDs] from [approved examples and rules]. Explain each expected result and its source. Include relevant failure and boundary cases. Identify uncovered behavior and weak mocks. Show that the tests detect the targeted incorrect behavior. Do not change approved expectations to fit code.

075.7 Implement one bounded change across files

Purpose Produce the complete implementation of one authorized increment.

Recommended practices Work from an identified repository baseline. Ask AI to read the relevant specification, design, contracts, and current files before editing. Let it coordinate changes across interfaces, implementation, storage, tests, and build files. Require minimal necessary changes and preserve unrelated work. Run focused checks during implementation.

Give or ask the AI Identify the task and approved artifacts. State allowed changes, compatibility requirements, evidence, and stop conditions. If AI needs a new dependency or a changed contract, require a proposal before it makes that decision. All source and configuration edits remain AI work.

Human decision and check Inspect the change summary and actual diff. Check whether AI changed tests, dependencies, public interfaces, or behavior outside the task. Resolve genuine design questions. Do not repair a small defect manually. Describe it and ask AI to correct it.

Common mistake → recovery AI changes many unrelated files or repeatedly rewrites the same component. Stop the task, inspect the diff, preserve valid work, and restore the last accepted state where needed. Narrow the task or revisit the design. Tool checkpoints do not replace version control. [19]

Exit evidence A coherent diff, focused check results, requirement links, and explicit blockers. No unapproved behavior change remains hidden in the patch.

Reusable prompt: Implement [task ID] against [approved artifact versions]. Preserve [contracts and behavior]. Change only what this task requires. Run [checks]. Report the files changed, results, and unresolved issues. Stop if completion requires an unapproved requirement, dependency, or design change.

Claude Code example. Use Plan Mode for repository inspection and the proposed approach. After approval, ask Claude to implement the named task and run its checks. Ask it to create or update project instructions through conversation. The user does not need to edit CLAUDE.md or source files. [5] [23]

When work runs in parallel. Start only after shared contracts are stable. Give each agent a separate work area and bounded task. Assign one integration owner. Review overlapping changes and run the combined suite after integration. A passing result from each isolated branch does not establish that the combined result passes.

085.8 Verify the integrated result

Purpose Establish whether the actual software meets the authorized requirements in the tested environment.

Recommended practices Combine the changes, then build and test the combined version. Use real dependencies for important integration behavior. Check output artifacts as well as exit codes. Record the tested commit, environment, commands, fixtures, and results. Distinguish passed, failed, skipped, and not-run checks.

Check What it can establish Important limit
Build, type check, and static analysis Structural consistency and selected defect patterns Successful compilation does not establish correct behavior.
Unit tests Local rules and boundaries Isolated substitutes can hide integration failures.
Integration and contract tests Real component behavior and interface expectations A contract test does not exercise the whole business workflow.
End-to-end tests Selected complete workflows A small set covers only selected paths.
Property and reference-result tests General rules or agreement with a trusted basis Input limits and oracle quality still restrict the conclusion.
Load, interruption, and recovery tests Behavior under specified operating conditions Results apply to the tested workloads and environments.

Pact documents contract testing for interactions between applications. This supplements the broader verification plan. [11]

Give or ask the AI Ask for a requirement-to-result table and raw output locations. Require measurements for performance claims. When an environment prevents a check, ask AI to mark the evidence gap instead of reporting success.

Human decision and check Confirm that tests ran against the release candidate. Inspect important failures, assertions, skipped tests, and unexpected changes to thresholds. Check both results and the reason those results are sufficient.

Common mistake → recovery “All tests passed” omits that half the suite did not run. Request the full test inventory and execution status. High coverage is a useful gap indicator, but does not establish adequate assertions or correct requirements. [13]

Exit evidence A reproducible evidence record with no unexplained failure or missing mandatory check.

Reusable prompt: Verify the combined change at [commit] against [requirement IDs]. Run the approved checks in [environment]. Report each command, outcome, measured value, and evidence location. Separate passed, failed, skipped, and not-run checks. Do not claim verification for a check you could not run.

095.9 Diagnose defects and recover deliberately

Purpose Correct the cause of a failure without weakening the requirement or damaging accepted behavior.

Recommended practices Reproduce the failure with the smallest useful case. Record expected and actual behavior. Ask AI to form a causal hypothesis and run a discriminating check before editing. Classify the problem as a requirement, design, code, test, data, or environment defect. Change the responsible artifact and rerun affected checks.

Give or ask the AI Supply logs, inputs, versions, reproduction steps, and the relevant requirement. Ask for the first failing boundary and evidence for the proposed cause. Keep failed attempts and their lessons in a short defect record.

Human decision and check Decide whether the original expected behavior remains correct. Approve any requirement or design change. Verify that AI did not delete an assertion, suppress an error, or broaden a tolerance merely to get a pass.

Failure pattern Recovery
No clear expected result Return to the requirement and its decision owner.
Intermittent failure Inspect uncontrolled state, timing, order, and shared resources. Preserve the failing evidence.
Repeated fixes produce new defects Restore an accepted baseline and reassess the design or task boundary.
AI repeats an unsuccessful approach Start a new session from the saved defect record and current artifacts.

pytest documents uncontrolled state and test-order effects as common causes of flaky tests. Repeated reruns alone do not repair those causes. [25]

Exit evidence A supported cause, an AI-written repair, and a regression check that detects the original defect. Record any remaining limitation.

Reusable prompt: Reproduce [failure] against [requirement and environment]. State expected and actual behavior. Rank possible causes and test the leading hypothesis. Repair the cause with the smallest coherent change. Preserve acceptance criteria. Show the regression result and affected-suite results.

Claude Code recovery limit. Its checkpoint documentation excludes file changes made through Bash from rewind coverage. Use repository history for code recovery. Treat external data recovery as a separate operation. [19]

105.10 Review and refactor for maintainability

Purpose Check whether the change is understandable, structurally sound, and suitable for future modification.

Recommended practices Review the actual diff against the specification and design. Ask a separate reviewer to seek counterexamples and unjustified complexity. Check error paths, data handling, dependencies, and tests. Require each finding to identify the affected requirement, file, consequence, and proposed remedy. Google’s review guidance addresses design, function, complexity, tests, naming, comments, and documentation. [14]

Give or ask the AI Supply the approved artifacts, diff, and evidence. Ask for findings before edits. Then authorize a bounded repair or refactoring task. Refactoring changes internal structure while preserving observable behavior. Treat a changed external result as a behavior change with its own approval. [15]

Human decision and check Assess high-impact findings and the explanation of critical paths. A reviewer must understand what the change does. If AI explanations remain unclear, request smaller changes or a clearer design. Writing zero code does not prevent a qualified human from reading the code.

Common mistake → recovery The same AI declares its own code “production-ready” without evidence. Require concrete findings and test results. Another model can broaden review, but shared assumptions can still produce shared mistakes. Reject cosmetic rewrites that increase review work without a stated benefit.

Exit evidence Findings are resolved or explicitly accepted. Refactoring preserves the approved behavior and passes affected checks.

Reusable prompt: Review [diff] against [specification, design, and evidence]. Report concrete defects, unnecessary complexity, and maintenance risks. Cite files and observable consequences. Do not edit yet. After approval, refactor only [scope], preserve external behavior, and rerun the affected checks.

115.11 Validate intended use and production readiness

Purpose Establish that the delivered behavior serves real tasks under the agreed operating conditions.

Recommended practices Use representative workflows, data sizes, timing, and failures. Observe actual outputs with a domain expert. Check the quality targets that unit tests cannot establish. Evaluate installation, repeated use, interruptions, recovery, and operational visibility. Choose reliability targets from the intended use. Service-level objectives make such targets measurable. [17]

Give or ask the AI Ask AI to prepare and execute acceptance scenarios, collect outputs, measure constraints, and identify unsupported claims. For an engineering calculation, compare units and numerical results with an approved reference. For a data workflow, reconcile counts, totals, rejected records, and rerun behavior.

Human decision and check Domain owners decide whether the results are useful and correct. Technical owners judge operating evidence. The release owner accepts the candidate or records the blocking gaps. AI can summarize the evidence, but cannot supply an absent business decision.

Common mistake → recovery A successful demonstration with a small fixture substitutes for operating evidence. Test the actual constraints in the release candidate. If the user task is wrong, change the specification and repeat affected stages.

Exit evidence Accepted user scenarios and measured production criteria. Failed or untested mandatory criteria block release. Appendix 2 defines this boundary within the report’s scope.

Reusable prompt: Assess [release candidate] for [approved user tasks and operating conditions]. Execute the acceptance scenarios and measure each quality target. Show actual outputs and unresolved gaps. Separate specification conformance from fitness for the intended use. Do not label untested criteria as passed.

125.12 Document, release, and hand over

Purpose Deliver software that another person can install, operate, diagnose, and change from retained information.

Recommended practices Ask AI to update usage instructions, interface references, design decisions, release notes, and recovery procedures. Generate all packaging and release scripts. Test the documented setup from a clean environment. Identify the exact release artifact and the source revision that produced it. Reliable release processes require repeatable builds and intentional configuration changes. [18]

Give or ask the AI Request a handover package with setup, execution, monitoring, failure diagnosis, data recovery, known limits, and ownership. Require a walkthrough by someone who did not implement the change. For a script, include scheduling, inputs, outputs, exit statuses, and safe rerun instructions.

Human decision and check Confirm that the documentation matches the release. Approve deployment at the planned decision point. Verify initial operation against the same acceptance criteria. Confirm that an owner can respond when the software fails.

Common mistake → recovery AI describes commands it did not run or claims that restoring old code reverses a data migration. Exercise setup and recovery in the representative environment. Record which data changes require a separate recovery procedure.

Exit evidence A versioned release, checked instructions, tested recovery procedures, ownership, and retained evidence.

Reusable prompt: Prepare the handover for [release]. Update all affected documents and generate the release artifacts. Test setup from a clean environment. Check recovery procedures against the actual data changes. Record known limits and owners. Present the release evidence before the deployment decision.

135.13 Maintain the specification through later changes

Purpose Preserve alignment as the system, dependencies, and requirements evolve.

Recommended practices Start each change from the current released baseline. Ask AI to map effects across requirements, contracts, consumers, data, tests, and operating instructions. Preserve stable IDs and mark superseded decisions. Revalidate relevant behavior after dependency upgrades. Use compatibility stages when old and new consumers must coexist.

Give or ask the AI Supply the change request and current artifacts. Ask for the proposed specification diff before implementation. Request a transition plan for interfaces and data. Expand–migrate–contract can separate adding a replacement interface, moving consumers, and removing the old interface. [16]

Human decision and check Approve changed intent and compatibility commitments. Decide what happens to existing data and clients. Check that new tests supplement existing obligations unless the approved specification explicitly replaces them.

Common mistake → recovery Code changes accumulate while the specification becomes stale. Stop the affected work and reconcile the differences. Separate intended changes, existing defects, and accidental drift. Do not revise the specification merely to describe whatever the code currently does.

Exit evidence A consistent new baseline of specification, design, code, tests, evidence, and documentation. Retain the prior release and the reasons for change.

Reusable prompt: Assess [change request] against the current release and approved artifacts. Identify affected requirement IDs, contracts, data, tests, and documents. Draft the specification changes and transition plan. Preserve existing commitments unless I approve their replacement. Implement only after the changed baseline is approved.

5.14 Adapt the same workflow to different systems

The artifacts scale with the problem. The obligation to define behavior and establish evidence remains.

System type Specification emphasis Evidence that matters
User-facing application User tasks, state transitions, validation rules, responsiveness, and accessibility needs Full workflows, persisted state, error recovery, and visual interaction checks
Microservice Interface contracts, timeouts, retries, duplicate handling, concurrency, and compatibility Consumer/provider checks, real dependency tests, interruption tests, and workload measurements
Operational script Inputs, file effects, exit statuses, reruns, interruption, and resource limits Representative files, malformed inputs, repeat execution, and a clean-environment run
Engineering workflow Units, assumptions, equations, numerical tolerance, and valid input ranges Reference calculations, boundary analysis, conservation rules, and reproducibility
Data workflow Schemas, missing values, duplicates, ordering, time rules, reconciliation, and schema changes Counts and totals, representative distributions, reruns, backfills, and recovery
Long-lived enterprise system Existing contracts, data migration, dependency life cycles, and incremental replacement Regression evidence, transition checks, compatibility results, and complete handover

6. Underlying concepts, terms, and principles

6.1 Principles that govern the workflow

Principle Consequence
Intent precedes implementation. Approve behavior before AI makes changes that depend on it.
Evidence precedes acceptance. A plausible explanation is not an executed test result.
The specification can change through an explicit decision. Preserve the reason and update affected artifacts.
Correctness needs an external basis. Check expected results against domain knowledge, contracts, or trusted references.
Small increments improve fault isolation. Review a coherent behavior change and its related files together.
Independence comes in degrees. A second AI review supplements other evidence. It does not guarantee an independent oracle.
Quality targets depend on use. Define operating conditions and thresholds before judging results.
Failure is information about a specific layer. Diagnose the requirement, design, code, test, data, or environment before repair.
Durable artifacts carry project memory. A new session starts from the repository state and saved decisions, not assumed chat memory.

6.2 Glossary

Definitions below use each term in the sense intended by this report.

Specification and decisions

Term Meaning
Acceptance criterion A condition that must hold before the responsible person accepts a result.
Artifact A retained project item, such as a specification, source file, test, or evidence record.
Baseline An identified, accepted version of the artifacts used as the starting point for work.
Constraint A limit on behavior or implementation, such as a required platform or maximum processing time.
Decision record A record of a technical choice, its reasons, alternatives, and consequences. Often called an architectural decision record.
EARS Easy Approach to Requirements Syntax. Patterns that structure natural-language requirements around conditions and responses.
Functional requirement A required behavior, such as rejecting a malformed input.
Invariant A condition that must remain true across the specified operations or states.
Nonfunctional requirement A required quality or constraint, such as latency, capacity, or maintainability.
Quality attribute A system characteristic that matters to its use, such as reliability or modifiability.
Quality-attribute scenario A condition, stimulus, and measurable response used to make a quality requirement concrete.
Specification An explicit description of required behavior and constraints against which work can be assessed.
Formal specification A specification expressed with mathematically defined syntax and semantics. A Markdown document does not meet this definition by itself.
Executable specification A machine-runnable representation of specified behavior, such as acceptance scenarios connected to tests. Prose alone does not execute.
Spec drift A difference between approved intent and the artifacts or behavior that should represent it.
Traceability Links between requirements, decisions, tasks, implementation, tests, and evidence.

AI and development tools

Term Meaning
Artificial intelligence (AI) The broader field and systems used here to interpret instructions and produce development artifacts.
Large language model (LLM) A trained model that generates text or structured outputs from its input. Its output can contain errors.
Coding agent A software system that selects development actions, invokes tools, and uses results to pursue a bounded task.
Agentic Describes a system’s use of action selection and environmental feedback with some autonomy.
Multi-agent system Multiple interacting agents with separately controlled actions. A set of role names in one prompt is not sufficient.
Prompt Instructions and relevant information sent to an AI model or coding tool.
Context The instructions, files, conversation, and tool results available to the model for a particular response.
Context window The finite amount of input and output information a model can process in one interaction.
Markdown A plain-text format for headings, links, lists, and other document structure.
Compaction A condensed representation of conversation history. It can omit details and does not replace authoritative project files.
Tool call An action request to software that reads, edits, executes, or inspects something outside the model’s text output.
Checkpoint A saved tool or conversation state with defined restoration limits.
Plan Mode A tool mode for inspection and proposed work before implementation. Exact permitted operations depend on the tool.
Integrated development environment (IDE) An application that combines code navigation, editing, execution, and other development tools.

Implementation and integration

Term Meaning
Application programming interface (API) A defined interface through which software components interact.
HTTP Hypertext Transfer Protocol. A protocol for exchanging requests and responses, commonly used by web services.
SQL Structured Query Language. A language used to define, query, and change data in many database systems.
Microservice A separately deployable service with a bounded responsibility and explicit interfaces.
Cohesion / coupling Cohesion concerns how closely a component’s responsibilities belong together. Coupling concerns dependencies between components.
Payload The data carried in a request, response, or message.
State / state transition State is the condition of a system at a point in time. A transition changes that condition.
Contract The agreed input, output, error, and interaction rules at a component boundary.
OpenAPI A language-independent specification format for HTTP APIs. It does not express every business rule by itself.
Schema The defined structure, types, and constraints of data.
Migration A controlled change to stored data, its structure, or an interface’s consumers.
Dependency Another component, library, tool, or service that the software requires.
Lockfile A file that records resolved dependency versions for repeatable installation.
Version control A system that records file revisions and supports comparison and recovery. Git is one example.
Commit An identified revision in version control.
Branch / worktree A branch tracks a line of revisions. A worktree gives a branch a separate working directory.
Diff The actual additions, changes, and deletions between file versions.
Vertical slice A bounded behavior implemented across all layers it needs.
Refactoring Internal restructuring that preserves observable behavior.
Regression Previously accepted behavior that fails after a change.
Compatibility The ability to continue meeting existing interface or data expectations after a change.
Idempotency Repeating an operation has the same intended effect as one execution within its stated conditions.
Transaction A group of data operations with defined consistency and commit behavior.
Concurrency Operations that progress during overlapping time periods and can interact through shared state.
Rollback Restoration of an earlier software or data state. Code rollback and data rollback can require different procedures.
Backfill Processing historical data to populate or correct a dataset under a defined rule.

Testing and release evidence

Term Meaning
Verification Assessment of whether the software meets its specified requirements.
Validation Assessment of whether the software fits its intended use.
Test oracle The basis for deciding whether an observed result is correct.
Assertion An executable test condition that checks an expected property or result. AI writes it in this workflow.
Fixture A controlled input or environment used for a test.
Mock A substitute that imitates a dependency in a test. Its behavior can differ from the real dependency.
Unit test A check of a small part of the software with limited dependencies.
Integration test A check of interactions between real components or dependencies.
Contract test A check that an interaction conforms to agreed consumer and provider expectations.
End-to-end test A check of a complete selected workflow through the system.
Characterization test A test that records current behavior, especially before changing an existing system.
Property-based test A test that generates inputs to seek violations of a stated general property.
Metamorphic test A test of an expected relation between results when inputs change in a defined way.
Mutation test A check that tests detect deliberate small changes to program behavior.
Static analysis / linter Checks that inspect code without exercising its complete runtime behavior. A linter often checks style and common error patterns.
Type check A check that operations and values obey a language’s type rules.
Coverage A measure of which code or requirements the tests exercise. Coverage alone does not measure assertion quality.
Flaky test A test that can pass or fail without an intended change to the assessed behavior.
Continuous integration (CI) Automated build and test checks applied as changes enter the shared codebase.
Build The process that converts source and configuration into runnable or distributable software.
Reproducible build A build whose inputs and environment are sufficiently controlled to repeat the stated result. Byte-identical output needs stricter controls.
Release candidate An identified version proposed for release and subjected to the required checks.
Service-level objective (SLO) A numerical reliability target measured over defined events or a time window.
Observability The ability to infer relevant internal behavior from outputs such as logs, metrics, and traces.
Evidence record Retained facts about what was checked, on which version, under which conditions, with which results.

Appendix 1. Concise end-to-end workflow checklist

Use this checklist for each release or material change. AI creates and updates the artifacts. Humans make the decisions in the right column.

Gate Evidence required Human decision
1. Outcome Defined users, tasks, scope, exclusions, and decision owners Is this the right problem and boundary?
2. Baseline Current system map, dependencies, environment, and existing test results Is the starting point correct?
3. Specification Stable IDs, complete behavior, approved examples, and measurable quality targets Are the rules and expected results correct?
4. Design Components, contracts, data rules, dependency choices, and failure behavior Are the trade-offs acceptable?
5. Plan Bounded increments, dependencies, tests, and completion evidence Is the work ready for implementation?
6. Test basis Credible expected results, fixtures, assertions, and requirement links Can these checks detect the important failures?
7. Implementation Complete multi-file change, focused test results, and a reviewable diff Does the change stay within its authorization?
8. Verification Combined build and test results, measurements, and explicit gaps Does the evidence support specification conformance?
9. Defect recovery Supported causes, repairs, and regression results Are the failures actually resolved?
10. Review Resolved findings and behavior-preserving refactoring evidence Is the code maintainable and technically sound?
11. Validation Representative user outcomes and operating evidence Does the release fit its intended use?
12. Handover Checked setup, release, recovery, documentation, and ownership Is the candidate ready to release and operate?
13. Continuity Updated specification, code, tests, evidence, and change history Can the next change start from a reliable baseline?

Stop conditions: A mandatory requirement remains undecided. A required check fails or did not run. AI changed the acceptance criteria without approval. The candidate differs from the tested version. The team cannot explain a material finding.

Session handover prompt: Record the current commit, approved artifact versions, completed tasks, open questions, failed attempts, test results, and next bounded task. A new session must read this record and the current files before it resumes work.

Appendix 2. The boundary between a prototype and production software

Production software has evidence that it can serve its intended use under defined operating conditions. A prototype establishes selected ideas or behaviors. Its evidence can leave substantial operating questions unanswered.

The difference is not the number of features, lines of code, users, or services. A narrow script can be production software. A large application with a polished interface can remain a prototype. AI authorship does not determine either classification.

This appendix describes the boundary. It does not recommend a prototype development stage.

Dimension Prototype-level evidence Production evidence within this report’s scope
Purpose and behavior Selected successful examples Approved requirements and representative acceptance outcomes
Inputs and state Convenient sample inputs Realistic ranges, malformed inputs, missing data, boundaries, and state transitions
Failure handling Manual correction or restart Specified failure outcomes and tested recovery
Data correctness Results look plausible Reconciliation, precision rules, persistence, and migration evidence
Repeat execution One successful run Defined duplicate, rerun, interruption, and concurrency behavior where relevant
Capacity and performance A small example runs Measured targets under a stated workload and environment
Integration Simulated or selectively checked dependencies Contract and real integration evidence for important boundaries
Delivery Runs on the original machine Repeatable setup, controlled dependencies, and an identified release artifact
Maintenance Original creator explains the system Clear structure, regression protection, current documents, and change history
Operation Someone watches the demonstration Useful diagnostics, an owner, and checked operating and recovery instructions

Practical release rule: Define each applicable production criterion before final acceptance. Record pass, fail, or not tested with its evidence. Explain why a criterion does not apply. An unresolved mandatory criterion blocks the release.

A production-ready increment can implement only one business capability. It must still meet the production criteria applicable to that capability. Deferring later features does not justify leaving its required behavior unverified.

Appendix 3. What is high-quality code?

High-quality code correctly implements the approved behavior and remains understandable, testable, and economical to change. It meets the system’s operating constraints without unnecessary complexity.

Code quality is one part of software quality. Good code cannot compensate for wrong requirements or an unsuitable architecture. A useful product can still contain code that is difficult to maintain.

Quality dimension What to examine Evidence or review question
Correctness Rules, boundaries, state changes, and failure paths Which requirement does this behavior implement? Which check would fail if it were wrong?
Clarity Names, control flow, comments, and local reasoning Can a qualified reviewer explain the important path and its assumptions?
Cohesion and coupling Responsibilities within components and dependencies between them Does one concept have a clear owner? Does a local change force unrelated changes?
Simplicity Abstractions, branching, duplication, and unused flexibility Which present requirement justifies this complexity?
Testability Observable results, controlled inputs, and separable dependencies Can tests exercise errors and boundaries without duplicating the implementation?
Reliability and data integrity Partial failures, repeat execution, consistency, and recovery What happens after an interruption at each important state boundary?
Efficiency Runtime, memory, storage, and dependency use Does measured behavior meet the agreed workload and resource limits?
Compatibility and changeability Interface stability, data evolution, and dependency effects Can the planned next change preserve existing obligations?
Diagnostics and documentation Useful error information, explanations, interfaces, and operating instructions Can another person diagnose a failure and identify the responsible behavior?

Google’s review guidance supports explicit review of structure and behavior. Refactoring supplies a disciplined way to improve internal design without changing external behavior. [14] [15]

Weak substitutes for quality: Large test counts, high coverage, short functions, extensive comments, a successful build, or an AI-generated score. Each can supply limited information. None establishes overall quality by itself.

A useful review outcome: List concrete defects and their consequences. Link each finding to evidence. Distinguish release blockers from bounded maintenance work. Use metrics to investigate a problem, then make the decision from the actual requirements and code.

Reusable quality-review prompt: Assess this change against the approved requirements and design. Examine correctness, clarity, complexity, testability, reliability, efficiency, and future changes. Cite concrete evidence for each finding. Identify release blockers separately. After approval, make the repairs and repeat the affected checks.
