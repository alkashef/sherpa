Deterministic checks
linters and type checkers save tokens and guarantee quality

Tests supply the missing guarantee.

Each requirement has an ID, and each test carries the ID of its requirement. So you do not trust the generator. You check its output against the spec. If the tests pass, the code satisfies the spec, even if two runs produce different code.

Deterministic tests, linters and type checkers must bound probabilistic AI generation.

per milestone
  • Checkers: programs that examine the code and report errors without a human. A type checker finds a number used where text is needed. A test runner runs the code and compares the result with the expected result. Examples: mypy, tsc, pytest.
  • Linters: programs that read the code and flag style problems and likely bugs, such as an unused variable. Many of them fix the problem by themselves. Examples: ruff, ESLint.
  • Branch coverage: the share of decision paths that the tests run. Each if statement has two paths, true and false. At 80%, the tests run four of every five paths. A path that no test runs can hide a bug.

Inside a new project
You getWhat it isWhy
CLAUDE.md, .claude/rules/ The rules Claude always loads, about 190 linesbigger context hurts, plus topic rules that load only when Claude touches a matching file. A short file is followed more reliably, and the Python rules cost nothing while Claude edits CSS.
docs/ The workflow and its documents: spec, design, plan, written with /write-spec, /write-design and /write-plan. The plan lists milestones with tests, model, effort and status. Claude works from these files, not from memory of past sessions. One fact, one file.
scripts/milestones-runner.py Runs the open milestones in order, each in a fresh session. Stops at a blocked milestone and prints the question; you approve in the plan, commit, run again. No session carries another’s context, and the runner stops instead of guessing.
Hooks, scripts/check.pyzero AI zero cost and deterministic Each edit: lint and fix. Each commit: all checks and tests. Lint errors, type errors and failing tests cannot reach the history.
Testing Every requirement has a test. Every user workflow has an end-to-end test. 80% branch coverage. The AI never weakens a test to make it pass. The tests prove the app does what the spec says.
.claude/settings.json Permissions: routine steps allowed, risky ones ask first, destructive ones denied (force push, hard reset). A rule here is enforced. A rule in CLAUDE.md is only advice.
Tool configs, .gitignore, config/.env Ruff, mypy, pytest, ESLint, Prettier and Stylelint, configured. Secrets and generated files kept out of git. The list of settings. Every project has the same layout and the same checks from the first commit.
Configuration Every setting lives in config/.env (never committed) and is listed in .env.example. No URLs, paths or thresholds inline. A missing value fails clearly at startup. One place to change behavior, and secrets stay out of the code.
Logging Set up once, in the entry point, from settings. Plain text, one line per event: time, level and module. Never log secrets. Ruff blocks print. You can see what the app did, and a failure leaves a trail.
Exception handling Catch an error only at an external boundary, add context and raise it again. Never swallow an error. The top level shows the full stack trace and stops. Failures are loud and traceable, not hidden.
requirements.txt The only list of dependencies. Direct ones only, pinned with ==. The AI asks before it adds one. The same tools and versions on every machine. No surprise packages.
